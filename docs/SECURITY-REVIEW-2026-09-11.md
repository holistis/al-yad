# Pre-publish security review, 2026-09-11

A record of an adversarial security review run against Yad's companion, extension and MCP server before shipping the version currently live. The goal is the same as every other document in this repo: you should not have to take this on trust. Every finding below points at a real commit, a real fix, and a real, runnable regression test that proves the specific gap is closed.

## Why this review happened

The same day (2026-09-11), a separate, confirmed vulnerability was found in an AI coding agent: a malicious MCP server could embed a hidden instruction inside a tool's `description` field, and the agent followed it with zero user interaction. Yad is exactly this shape of software, a local companion that gives an AI agent real control over a real, logged-in browser, so the same kind of adversarial reading was run against this codebase rather than waiting for something to go wrong first.

## What this review is, honestly

This was our own adversarial code review, not an independent third-party audit. No external auditor was engaged. What makes the findings below checkable regardless: every one has a specific file and line, a concrete attack scenario, and a regression test you can run yourself. Verify the claims by reading the code and running the tests, not by trusting this document's prose.

## Findings and fixes

| # | Severity | What it was | Fix | Regression test |
| --- | --- | --- | --- | --- |
| 1 | Critical | The local HTTP API on `127.0.0.1:3747` had no authentication on the loopback path. A valid local address plus a matching Host header only proves the TCP packet came from this machine, not who sent it: any other browser tab open in the same Chrome, or any other local process, could drive the full API, including arbitrary JS execution via `/cdp/evaluate` and starting the autonomous agent via `/goal`. | A one-time generated, persisted token (`X-Yad-Token` header), required on every route except `GET /status`. Token file written owner-only (0600) where the platform honors it. | `http-api.auth.test.ts` |
| 2 | High | Bundled in the same fix: `/fs/read-file`, `/fs/list-files` and `/fs/search-files` accepted any absolute path instead of restricting it to the documented Desktop/Documents/Downloads allowlist. | Rejects any path outside that allowlist. | same file |
| 3 | High | Bundled in the same fix: `cleanWithGroq()`, a second, independent AI-call path used to clean up raw extraction results, never went through `SpendGuard`, so a killed or capped spend guard could still be silently bypassed. | Routed through the same `SpendGuard.checkBefore()`/`record()` choke point as every other AI call. | same file |
| 4 | High | `resolveRunTab()`'s failure path (when `chrome.tabs.create()` fails) fell back to "query all open http(s) tabs, sort by lastAccessed, take the top one". This is the exact heuristic behind a real, already-fixed 2026-09-07 incident where it read a user's live Roundcube mailbox instead of a Yad-owned tab. This was the one remaining place still using that heuristic, reachable through a rarer path. | No fallback to the user's most-recently-active tab. On a failed `tabs.create()`, returns `null` honestly; every caller already handled `null` as "no active tab" correctly. | `native-port.resolveRunTab.test.ts` |
| 5 | Medium/High | `/adopt-tab` matched a target pattern with a bare `url.includes(pattern)`. A pattern like `amazon.com` also matched a lookalike domain such as `scam-amazon.com.evil.ru` that happens to contain the same substring, letting the agent adopt and trust a phishing tab as if it were the real site. | Patterns that look like a bare hostname now match on the real hostname (exact or subdomain) via `new URL()`. Patterns containing `/`, `?` or `#` keep the old substring behavior, since those are meant to match a path or query. | `native-port.urlMatchesAdoptPattern.test.ts` |
| 6 | High | `roleOf()` gave a non-semantic clickable element (e.g. `<div onclick="submitOrder()">`, no ARIA role) just its bare tag name (`"div"`). The fail-closed confirmation gate that is supposed to make every click on a mutating role require confirmation, regardless of label, never triggered, because `"div"` isn't in the `WRITE_ROLES` list of real ARIA role names. A checkout button built as a bare div with a click handler bypassed both the role check and, with an unusual label, the word-based deny check too. | An element with an `onclick` attribute and no explicit role now gets `role="button"`. An explicit ARIA role always still wins. | `perception.roleOf.test.ts` |
| 7 | Medium | `DENY_WORDS` matched the base Dutch verb form (`betaal`, `bestel`) but not its conjugations: "Betalen" as a button label slipped through, because Dutch open-syllable spelling means it is not a plain substring of "betaal". Common English buy CTAs (Buy Now, Purchase, Complete Order, Finish Order, Confirm Payment) were also missing. Separately, `pathIsDenied()` only checked the URL path, not the hostname, so a payment processor's own checkout (e.g. `checkout.stripe.com/c/pay/cs_xxx`, no "checkout" or "payment" in the path itself) was never recognized as a payment page. | Extended `DENY_WORDS` to cover conjugations and the missing English CTAs. Added `PAYMENT_HOSTS`, a hostname allowlist of known payment processors (Stripe, PayPal, Adyen, Mollie, Worldpay, Google Pay, Klarna, Shopify checkout) as a second, independent layer next to the path check. | `guardrails.test.ts`, including a test proving a spoofed subdomain (`notcheckout.stripe.com.evil.nl`) does not falsely match. |
| 8 | Medium | Same family, found the same day: `DENY_PATHS` was English-only (`/payment`, `/checkout`, `/order`) while `DENY_WORDS` already covered Dutch button text. A Dutch webshop routing checkout under `/afrekenen`, `/bestellen`, `/betalen` or `/kassa` instead of the English `/checkout` was never caught by the path check, only by the (now more complete) word check. | Added `/afrekenen`, `/bestellen`, `/bestelling`, `/betalen`, `/kassa` to `DENY_PATHS`. | 6 regression tests, including the SPA hash-route variant (`#/afrekenen`). |
| 9 | Medium | `isAborted()` was only checked right after a fresh LLM call. A 1-3 step micro-plan executes without a new model call, so steps already queued kept running after the user clicked Stop. | `isAborted()` is now also checked right before executing a buffered step, inside `waitForCondition()`, and before every `chatWithRetry()` attempt. The extension now also sends `ABORT_RUN` to the companion the moment Stop is clicked, not only when the tab closes. | A 2-step micro-plan where `isAborted()` becomes true after the first action now stops after exactly 1 action instead of 2. |
| 10 | High | The RSA private key generated for the extension (`ext-private.pem`) was written with `writeFileSync()` using the process umask, which can leave it group- or world-readable on a shared Linux or macOS machine. Anyone who can read this key can forge the extension ID and impersonate the paired extension to the companion. | `chmodSync(privPath, 0o600)` after writing, and also when reusing an existing key (for keys predating this fix). Both calls are best-effort: Windows' chmod has a different, more limited meaning, so this is not a regression there. | Regression tests that `statSync()` the actual written key and check its mode bits on non-Windows platforms. |
| 11 | Low | The code comment "Prompt-injectie blokkeren" above the goal-sanitization step in `http-api.ts` and `main-server.ts` implied a general defense against prompt injection. In reality that filter only screens the text the caller (Claude Code, or the king) types as a task, never the page text that lands in the same prompt later, which is the actual untrusted input this class of filter normally exists to stop. A page literally containing "ignore previous instructions" reaches the model completely unfiltered via `snapshot.textDigest`; only the explicit `UNTRUSTED PAGE CONTENT` marker in `prompt.ts` still guards against that. | Comment-only correction. Both files now honestly describe what the filter does and does not do, and point at where the real protection against page-text injection lives. | none needed, no behavior changed |
| 12 | Low | `security.html` claimed unconditionally that a key is "never written to disk in readable form". True for a key pasted into the extension (genuinely DPAPI-encrypted, correctly described). Not true for a key placed in a developer's own `.env` file, the documented path for running the companion from source, since `env.ts` reads that straight into `process.env` with no encryption. This project runs that way itself. | Added an explicit, honest paragraph that keeps the proven DPAPI claim standing but states plainly that a `.env` key stays as readable as any `.env` file, protected by the operating system's own file permissions, not by this encryption mechanism. | none needed, no behavior changed |

Full technical detail for each finding: the commit history on `security/adversarial-review-fixes` (merged into `main` via PR #37), and the regression tests referenced above.

## What this does NOT prove

- This is not an independent audit. No external party has verified these findings or fixes. If that matters for your use case, verify the fixes yourself against the commit history and the tests referenced above.
- A security review finds what it looks for. It is evidence of care taken, not proof that no other issue exists.
- Findings 11 and 12 are documentation/comment corrections, not exploitable code paths. They're included here for completeness, not because they carry the same risk as the others.
- This table covers the findings closed in PR #37, one wave of a broader adversarial review conducted the same day; it is not a claim that every candidate the review considered is listed here.

## Open, ongoing work

An internal check run against Yad's own MCP tool descriptions the day after this review surfaced one candidate worth naming here: `yad_run_goal` both reads whatever page it lands on and acts on the browser, and its own description claims a confirmation gate. That gate is real, but scoped specifically to payment and checkout, not to browser actions in general, by design (checked against `packages/companion/src/gate/guardrails.ts`). This is a candidate, not a confirmed finding: it has not yet gone through a full reachability chain, a working proof of concept, or an adversarial second read. Listed here in the same spirit as the rest of this document, so a candidate under active investigation is visible rather than silent until it either survives verification or is refuted.
